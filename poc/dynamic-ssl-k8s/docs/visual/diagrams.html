● The problem

When a partner rotates its certificate, our calls start failing

Our services call 50+ outside APIs over HTTPS. Each partner proves who it is with a digital certificate, signed by a trusted authority. We only accept partners whose authority is on our trust list.

Cost today

In plain terms
Think of a bouncer with a guest list. The partner showed up with an ID from an issuer the bouncer doesn't recognize — so they're turned away at the door.

● The fix

Update what we trust — live, with zero restarts

Instead of rebuilding containers, we change one config file. The running service picks it up and swaps its trust list in memory — open connections and the process keep running.

1

The service notices

A watcher sees the mounted file change inside the pod.

3

It swaps trust in memory

The trust list is replaced atomically, under a lock.

hot TrustManager swap
Calls work again

Same process, no redeploy, no downtime.

0 restarts
In plain terms
We just handed the bouncer an updated guest list through the door — the club never closed, and the new guests now get in.
Proven
Measured end-to-end on Kubernetes: call works → partner rotates → call fails → config updated → call recovers in ~60s, same pod, RESTARTS = 0.

● Under the hood

Why no restart is needed

The whole networking stack is built once and never rebuilt. Only the innermost “trust list” is swapped — so the connection pool, sockets, and TLS engine stay exactly where they are.

Built once · never rebuilt
Stable references mean in-flight requests and pooled connections are untouched.
